# RepoReaper 数据流分析文档

## 📋 项目概述

RepoReaper 是一个基于 RAG（检索增强生成）的智能代码分析系统，通过自治 Agent 自动分析 GitHub 仓库的架构和代码逻辑。系统将 LLM 视为 CPU，将向量数据库视为 L2 智能缓存，实现动态的代码理解和问答。

## 🏗 系统架构

```
┌─────────────┐
│  前端 (Web)  │
│  index.html  │
└──────┬──────┘
       │ HTTP/SSE
       ▼
┌─────────────────────────────────────┐
│         FastAPI 主服务               │
│         app/main.py                  │
│  - /analyze (仓库分析)                │
│  - /chat (问答对话)                  │
│  - /repo-tree (目录树)               │
└──────┬──────────────────┬───────────┘
       │                  │
       ▼                  ▼
┌──────────────┐   ┌──────────────┐
│ Agent Service│   │ Chat Service │
│ (分析流程)    │   │ (问答流程)   │
└──────┬───────┘   └──────┬───────┘
       │                  │
       ├──────────────────┤
       │                  │
       ▼                  ▼
┌─────────────────────────────────────┐
│      核心服务层                       │
│  - GitHub Service (代码获取)          │
│  - Chunking Service (代码分块)        │
│  - Vector Service (向量存储)          │
│  - LLM Client (大模型调用)            │
└─────────────────────────────────────┘
```

## 🔄 数据流详解

### 一、仓库分析流程 (Agent Service)

**入口**: `GET /analyze?url=<repo_url>&session_id=<id>&language=<lang>`

#### 1.1 初始化阶段

```
用户输入 GitHub URL
    │
    ▼
[main.py] /analyze 路由
    │
    ▼
[agent_service.py] agent_stream()
    │
    ├─→ 创建 VectorStore (session_id)
    ├─→ 重置向量集合 (reset_collection)
    └─→ 初始化 UniversalChunker
```

**数据流**:
- **输入**: `repo_url`, `session_id`, `language`
- **输出**: SSE 流式事件 (`{"step": "init", "message": "..."}`)

#### 1.2 仓库结构获取

```
[agent_service.py]
    │
    ▼
[github_service.py] get_repo_structure()
    │
    ├─→ 解析 URL → owner/repo
    ├─→ GitHub API 获取文件树
    ├─→ 过滤文件 (忽略 .git, node_modules 等)
    └─→ 返回文件列表 file_list[]
```

**数据流**:
- **输入**: `repo_url` (如 `https://github.com/user/repo`)
- **处理**: 
  - 使用 PyGithub 调用 GitHub API
  - 过滤规则: 忽略图片、二进制、依赖目录
- **输出**: `file_list` (扁平文件路径列表)

#### 1.3 仓库地图生成 (Repo Map)

```
[agent_service.py] generate_repo_map()
    │
    ├─→ 筛选优先级文件 (main, app, core, api 等)
    ├─→ 并发处理文件 (asyncio.gather)
    │   │
    │   └─→ [github_service.py] get_file_content()
    │       │
    │       └─→ GitHub API 获取文件内容
    │
    └─→ [agent_service.py] _extract_symbols()
        │
        ├─→ Python: AST 解析 (类/函数签名)
        ├─→ Java/TS/Go: 正则表达式提取
        └─→ 生成符号地图
```

**数据流**:
- **输入**: `file_list[]`, `repo_url`
- **处理**:
  - 优先级筛选: 选择包含 `main`, `app`, `core`, `api` 等关键词的文件
  - 多语言符号提取:
    - Python: 使用 `ast.parse()` 提取类和函数
    - 其他语言: 使用正则表达式匹配类/函数定义
- **输出**: `repo_map_str` (包含文件路径和符号签名的文本)

**示例输出**:
```
--- Key Files Structure (Top 15) ---
app/main.py
  [F] read_root
  [F] analyze
app/services/agent_service.py
  [F] agent_stream
  [F] generate_repo_map
  [C] UniversalChunker
    - chunk_file
```

#### 1.4 智能文件选择循环 (ReAct Pattern)

```
[agent_service.py] agent_stream() - 循环 3 轮
    │
    ├─→ Round 1: LLM 分析 Repo Map
    │   │
    │   ├─→ 构建 Prompt:
    │   │   - Repo Map (文件结构)
    │   │   - 已读文件列表
    │   │   - 当前知识摘要
    │   │
    │   ├─→ [llm_client.py] LLM 调用
    │   │   - 模型: DeepSeek/Kimi/Groq
    │   │   - 任务: 选择 1-3 个关键文件
    │   │
    │   └─→ 解析 JSON 响应 → target_files[]
    │
    ├─→ 下载并处理文件
    │   │
    │   ├─→ [github_service.py] get_file_content()
    │   │   └─→ 获取文件原始内容
    │   │
    │   ├─→ [chunking_service.py] chunk_file()
    │   │   │
    │   │   ├─→ Python: AST 感知分块
    │   │   │   - 按类/方法切分
    │   │   │   - 大类拆解时注入父类上下文
    │   │   │
    │   │   ├─→ C-Style: 括号层级分块
    │   │   │   - Java/JS/TS/Go 等
    │   │   │
    │   │   └─→ 其他: 固定行数切分
    │   │
    │   └─→ [vector_service.py] add_documents()
    │       │
    │       ├─→ 生成 Embeddings (BAAI/bge-m3)
    │       ├─→ 存储到 ChromaDB
    │       └─→ 更新 BM25 索引
    │
    └─→ 更新上下文摘要
        │
        └─→ [vector_service.py] save_context()
            └─→ 保存到 data/contexts/{session_id}.json
```

**数据流**:
- **输入**: `repo_map_str`, `visited_files`, `context_summary`
- **LLM Prompt**:
  ```
  [Task]
  Select 1-3 MOST CRITICAL files to read next.
  Return ONLY a raw JSON list: ["file1.py", "file2.py"]
  ```
- **处理**:
  - LLM 返回文件路径列表
  - 并发下载文件内容
  - AST 感知分块 (保持代码逻辑完整性)
  - 向量化并存储
- **输出**: 
  - 更新 `visited_files` 集合
  - 更新 `context_summary` 文本
  - 持久化到 JSON 文件

#### 1.5 架构报告生成

```
[agent_service.py] agent_stream() - 最终阶段
    │
    ├─→ 构建分析 Prompt
    │   - 已分析文件列表
    │   - 代码知识摘要 (context_summary)
    │   - 语言特定指令 (中文/英文)
    │
    ├─→ [llm_client.py] 流式生成报告
    │   - 模型: DeepSeek/Kimi/Groq
    │   - 格式: Markdown + Mermaid 图表
    │   - 内容:
    │     * 执行摘要
    │     * 系统架构图
    │     * 核心逻辑分析表
    │     * 关键方法深度解析
    │     * 主要工作流时序图
    │     * 快速开始指南
    │
    └─→ SSE 流式返回给前端
```

**数据流**:
- **输入**: `visited_files[]`, `context_summary` (前 15000 字符)
- **LLM Prompt**: 根据 `language` 参数选择中英文模板
- **输出**: SSE 流式事件 (`{"step": "report_chunk", "chunk": "..."}`)

### 二、问答对话流程 (Chat Service)

**入口**: `POST /chat` (JSON: `{query, session_id, model}`)

#### 2.1 查询预处理

```
[chat_service.py] process_chat_stream()
    │
    ├─→ 检测语言 (is_chinese_query)
    │   └─→ 判断是否包含中文字符
    │
    └─→ [chat_service.py] _rewrite_query()
        │
        ├─→ LLM 查询重写
        │   - 输入: 用户自然语言 ("鉴权在哪里？")
        │   - 输出: 英文关键词 ("auth login verify")
        │
        └─→ 目的: 提高 BM25/Vector 检索命中率
```

**数据流**:
- **输入**: `user_query` (可能是中文)
- **处理**: LLM 将自然语言转换为技术关键词
- **输出**: `search_query` (英文关键词字符串)

#### 2.2 混合检索 (Hybrid Search)

```
[chat_service.py] process_chat_stream()
    │
    └─→ [vector_service.py] search_hybrid()
        │
        ├─→ Dense Retrieval (向量检索)
        │   │
        │   ├─→ [vector_service.py] embed_text()
        │   │   └─→ SiliconFlow API (BAAI/bge-m3)
        │   │
        │   └─→ ChromaDB 查询
        │       └─→ 返回 top_k*2 个结果
        │
        ├─→ Sparse Retrieval (BM25)
        │   │
        │   ├─→ [vector_service.py] _tokenize()
        │   │   └─→ 分词处理
        │   │
        │   └─→ BM25Okapi 评分
        │       └─→ 返回 top_k*2 个结果
        │
        └─→ Reciprocal Rank Fusion (RRF)
            │
            ├─→ 融合两种检索结果
            ├─→ 加权排序 (vector: 1.0, bm25: 0.3)
            └─→ 返回 top_k 个最终结果
```

**数据流**:
- **输入**: `search_query` (重写后的查询)
- **处理**:
  - **向量检索**: 
    - 查询文本 → Embedding (1024 维)
    - ChromaDB 余弦相似度搜索
  - **BM25 检索**:
    - 查询文本 → 分词
    - 计算 TF-IDF 分数
  - **融合**: RRF 算法合并排序
- **输出**: `relevant_docs[]` (包含 content, metadata, score)

#### 2.3 上下文构建

```
[chat_service.py] process_chat_stream()
    │
    ├─→ [chat_service.py] _build_context()
    │   └─→ 格式化检索结果
    │       - 文件路径
    │       - 类名 (如果有)
    │       - 代码片段 (前 2000 字符)
    │
    ├─→ [vector_service.py] global_context
    │   └─→ 从 data/contexts/{session_id}.json 加载
    │       - file_tree: 仓库地图
    │       - summary: Agent 分析摘要
    │
    └─→ 构建完整 Prompt
        │
        ├─→ System Instruction
        │   - 角色定义
        │   - 语言指令 (中/英)
        │   - 工具使用说明
        │
        ├─→ Global Context
        │   - Repo Map
        │   - Agent Analysis Summary
        │
        ├─→ Current Code Context
        │   - 检索到的代码片段
        │
        └─→ User Query
            - 原始用户问题
```

**数据流**:
- **输入**: `relevant_docs[]`, `global_context`
- **处理**: 组装多层级上下文
- **输出**: `system_instruction`, `augmented_user_query`

#### 2.4 LLM 推理与工具调用

```
[chat_service.py] process_chat_stream()
    │
    ├─→ Phase 1: 初始回答
    │   │
    │   ├─→ [llm_client.py] 流式生成
    │   │   - 模型: 根据 model_provider 选择
    │   │   - 输入: 完整 Prompt
    │   │   - 输出: 流式文本
    │   │
    │   └─→ 实时检测 <tool_code> 标签
    │       └─→ 提取文件路径列表
    │
    └─→ Phase 2: Just-In-Time 文件拉取 (如果检测到工具调用)
        │
        ├─→ [chat_service.py] _download_and_index()
        │   │
        │   ├─→ [github_service.py] get_file_content()
        │   │   └─→ GitHub API 获取文件
        │   │
        │   ├─→ [chunking_service.py] chunk_file()
        │   │   └─→ 代码分块
        │   │
        │   └─→ [vector_service.py] add_documents()
        │       └─→ 实时索引到向量库
        │
        └─→ Phase 3: 最终回答
            │
            └─→ [llm_client.py] 再次生成
                - 输入: 原始问题 + 新加载的代码上下文
                - 输出: 完整答案
```

**数据流**:
- **Phase 1 输入**: 完整 Prompt (包含检索上下文)
- **Phase 1 输出**: 流式文本 + 可能的 `<tool_code>path/to/file</tool_code>` 标签
- **Phase 2 处理**:
  - 解析工具调用标签
  - 下载缺失文件
  - 实时索引到向量库
- **Phase 3 输入**: 原始问题 + 新代码上下文
- **Phase 3 输出**: 最终完整答案

### 三、核心服务详解

#### 3.1 GitHub Service (`github_service.py`)

**职责**: 与 GitHub API 交互，获取仓库代码

**主要函数**:
- `parse_repo_url(url)`: 解析 URL → `owner/repo`
- `get_repo_structure(url)`: 获取文件列表 (扁平)
- `get_repo_tree(url)`: 获取目录树 (嵌套字典)
- `get_file_content(url, path)`: 获取单个文件内容

**数据流**:
```
GitHub URL
    │
    ▼
PyGithub API
    │
    ├─→ get_git_tree() → 文件列表
    └─→ get_contents() → 文件内容
```

#### 3.2 Chunking Service (`chunking_service.py`)

**职责**: 智能代码分块，保持逻辑完整性

**分块策略**:
1. **Python (AST 感知)**:
   - 按类和函数切分
   - 大类拆解时注入父类上下文
   - 最小块大小: 50 字符
   - 最大块大小: 2000 字符

2. **C-Style 语言** (Java/JS/TS/Go):
   - 基于花括号 `{}` 层级识别
   - 提取类/函数名作为元数据

3. **其他文件**:
   - 固定行数切分 (100 行/块)

**数据流**:
```
原始代码文件
    │
    ├─→ Python → AST 解析 → 类/方法块
    ├─→ C-Style → 括号匹配 → 代码块
    └─→ 其他 → 固定行数 → 文本块
    │
    └─→ 输出: chunks[] (content + metadata)
```

#### 3.3 Vector Service (`vector_service.py`)

**职责**: 向量存储和混合检索

**存储架构**:
- **ChromaDB**: 持久化向量数据库
  - 路径: `data/chroma_db/`
  - Collection 命名: `repo_{session_id}`
- **BM25 索引**: 内存中维护 (每次请求重建)
- **上下文 JSON**: `data/contexts/{session_id}.json`

**检索流程**:
```
查询文本
    │
    ├─→ Embedding API (BAAI/bge-m3) → 向量
    │   └─→ ChromaDB 查询 → 向量结果
    │
    ├─→ 分词 → BM25 评分 → BM25 结果
    │
    └─→ RRF 融合 → 最终排序结果
```

**数据流**:
- **写入**: `add_documents(documents, metadatas)`
  - 批量生成 Embeddings
  - 存储到 ChromaDB
  - 更新内存 BM25 索引
- **读取**: `search_hybrid(query, top_k)`
  - 向量检索 + BM25 检索
  - RRF 融合排序

#### 3.4 LLM Client (`llm_client.py`)

**职责**: 统一的大模型调用接口

**支持的 Provider**:
- **DeepSeek**: OpenAI 兼容 API
- **Groq**: 异步 Groq SDK
- **Kimi**: GitCode API (OpenAI 兼容)

**数据流**:
```
LLM 请求
    │
    ├─→ 根据 provider 选择客户端
    │   - DeepSeek → AsyncOpenAI (deepseek.com)
    │   - Groq → AsyncGroq
    │   - Kimi → AsyncOpenAI (gitcode.com)
    │
    └─→ 统一接口: chat_completions_create()
        - 支持流式输出
        - 支持自定义参数
```

### 四、数据持久化

#### 4.1 向量数据 (ChromaDB)

**存储位置**: `data/chroma_db/`

**结构**:
- 每个 Session 一个 Collection: `repo_{session_id}`
- 文档 ID: `{file_path}_{index}`
- 元数据: `{file, type, name, class}`

**生命周期**:
- 创建: Agent 分析时
- 更新: Chat 时 JIT 拉取文件后
- 清理: 24 小时自动清理 (main.py cleanup_cron_job)

#### 4.2 上下文数据 (JSON)

**存储位置**: `data/contexts/{session_id}.json`

**结构**:
```json
{
  "repo_url": "https://github.com/user/repo",
  "global_context": {
    "file_tree": "...",
    "summary": "..."
  }
}
```

**用途**:
- 跨 Worker 共享上下文 (无状态设计)
- 前端刷新后恢复状态

#### 4.3 会话管理

**Session ID**: 由前端生成 (UUID)

**存储映射**:
- `session_id` → ChromaDB Collection
- `session_id` → Context JSON 文件
- `session_id` → 内存中的 BM25 索引 (临时)

### 六、关键技术点

#### 6.1 AST 感知分块

**优势**: 保持代码逻辑完整性，避免函数被截断

**实现**:
- Python: 使用 `ast.parse()` 解析语法树
- 大类拆解: 将父类 Docstring 注入到每个方法块

#### 6.2 混合检索 (Hybrid Search)

**优势**: 兼顾语义理解和精确匹配

**策略**:
- **向量检索**: 捕捉语义相似性 (如 "登录" ↔ "authentication")
- **BM25 检索**: 精确匹配变量名、函数签名
- **RRF 融合**: 加权合并两种结果

#### 6.3 Just-In-Time (JIT) 文件拉取

**优势**: 动态扩展知识库，避免全量索引

**触发条件**: LLM 检测到上下文不足，输出 `<tool_code>` 标签

**流程**:
1. LLM 识别缺失信息
2. 输出工具调用标签
3. 系统拦截标签
4. 拉取文件并实时索引
5. 重新生成答案

#### 6.4 无状态设计

**优势**: 支持多 Worker 并发，无锁竞争

**实现**:
- ChromaDB: 持久化存储，多进程共享
- Context JSON: 磁盘文件，跨进程读取
- BM25: 内存索引，每次请求重建 (轻量级)

## 📝 总结

RepoReaper 的数据流设计体现了以下核心思想:

1. **RAG 作为智能缓存**: 向量库不是静态数据库，而是动态扩展的上下文缓存
2. **自治 Agent**: LLM 主动选择关键文件，而非被动检索
3. **Just-In-Time 学习**: 检测到信息缺失时实时拉取文件
4. **混合检索**: 结合语义理解和精确匹配，提高检索质量
5. **无状态架构**: 支持多 Worker 并发，通过持久化存储共享状态

整个系统实现了从"静态索引"到"动态理解"的范式转变，让代码分析更加智能和高效。
